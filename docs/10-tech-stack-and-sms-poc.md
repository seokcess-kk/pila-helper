# 10. 기술 스택 결정 · SMS 캡처 PoC 설계

> 목적: 스프린트 0 착수의 전제. ① 기술 스택 추천/근거 ② **SMS 캡처 PoC**(차별화의 기술 전제) 설계.
> 전제: 단일 반응형 웹앱(PWA)+역할 뷰([05 C-7]) · 운영/재무 구역([05 D-6]) · 멀티테넌시 PG([06]) · SMS 손익 wedge([05 D-5]).

---

## 0. 핵심 제약부터 (설계를 좌우함)

1. **SMS/알림 캡처는 웹으로 불가** → **오너 폰에 네이티브 안드로이드 컴패니언**이 필요. (iOS는 SMS 접근 불가)
   - C-7("단일 웹앱")과 모순 아님: 제품 UI는 여전히 하나의 웹앱. 컴패니언은 **데이터 수집 유틸리티**(스캐너 같은 보조 장치).
2. **금융·민감 정보** → 데이터 레지던시(국내 리전 권장) + 암호화 + owner 게이트.
3. **소팀·빠른 구현** → 단일 언어(TypeScript) 모놀리스로 속도 극대화, 트랙(운영/재무) 병렬.

## 1. 스택 (✅ 확정 2026-06)

> **TS/Next 모놀리스 + Vercel(icn1 서울) + Supabase(서울) + Inngest** — 글로벌 매니지드·저운영,
> 데이터는 서울 리전 핀. SMS 캡처만 **Kotlin 안드로이드 컴패니언**. → 근거·대안은 아래 표.

## 2. 배포 단위 3개 (아키텍처)

```
[오너 안드로이드 폰]
  Android 컴패니언(Kotlin)
   ├ NotificationListener / SMS 수신 → 금융 발신자 화이트리스트 파싱
   └ HTTPS POST /ingest  (Idempotency-Key) ───────────────┐
                                                          ▼
[웹앱 PWA · Next.js] ── 운영 콘솔 / 재무 어드민🔒 / 회원앱 (역할 뷰)
   │  서버액션·REST
   ▼
[백엔드 API + 잡] ──── Inngest (만료알림·SMS처리·판매↔입금 대사)
   │                         │
   ▼                         ▼
[PostgreSQL (Seoul)]   [S3 스토리지(영수증)]
   ▲
[외부] Solapi(문자/알림톡) · 카카오 로그인 · (v1) 마이데이터 제휴
```

- **웹앱 = 제품**(운영/재무/회원). **컴패니언 = 오너 전용 수집 유틸**. **워커 = 잡·인입·대사**.
- 백엔드는 Next 모놀리스에 포함, 백그라운드 잡은 **Inngest**(매니지드)로 — 별도 워커/Redis 운영 불요.
- 민감 금융 페이로드는 우리 DB 보관, Inngest엔 **ID/참조만** 전달(원문 미경유).

## 3. 인증(한국 휴대폰) 설계

- **MVP = 휴대폰 SMS OTP**: 번호 입력 → 인증번호(Solapi 문자) → 검증 → 세션. 회원 가입/로그인 공통.
- **스튜디오 게이트**: 회원은 초대 링크로 진입 → OTP → 동의 → `phone` 매칭으로 운영자 등록 프로필 연결([07]).
- **소셜**(카카오/네이버) = 편의 옵션.
- **통신사 본인인증(NICE/KCP, 주민번호 연계)** = 필요 시(법적/정산 요건) 도입. MVP는 OTP로 충분.

## 4. 보안·컴플라이언스 (NFR 연계)

- **재무 구역 owner 게이트**(D-6): 라우트·API 권한 분리, 필요 시 재인증.
- **암호화**: 금융 거래·건강(민감) 정보 at-rest 암호화(컬럼/앱레이어) + 접근 로그.
- **데이터 레지던시**: 금융·개인정보는 **국내 리전** 권장.
- **SMS 캡처 고지·동의**: 오너 본인 기기·명시 동의, **금융 발신자만**, 원문 최소 저장(파싱 결과 위주) → 개인정보 처리방침 반영(NFR-2).
- **시크릿·백업·모니터링**(NFR-3).

## 5. ★ SMS 캡처 PoC 설계 (스프린트 진입 전 스파이크)

### 5.1 가설
> "오너의 **안드로이드** 폰에서 카드 승인·입금 문자를 **자동 수집·파싱**해 거래원장에
> **90%+ 정확도**로 등록할 수 있는가? 그리고 **배포가 정책적으로 가능한가?**"

### 5.2 캡처 방식 (둘 다 검증, 정책상 ①선호)
| 방식 | 무엇 | 장점 | 제약 |
|------|------|------|------|
| ① **NotificationListenerService** | 알림(은행·카드 앱 푸시 + 문자앱 알림) 텍스트 | 앱푸시까지 포괄, **Play 정책 상대적 우호** | 사용자가 알림 접근 권한 수동 허용 |
| ② SMS BroadcastReceiver(READ/RECEIVE_SMS) | 문자 원문 | 직접·정확 | **Google Play SMS 권한 정책 매우 제한**(기본 문자앱 등) → 거절 위험 |

> 결론 후보: **①NotificationListener 우선**, ②는 보조/사이드로드 한정.

### 5.3 파싱
- **발신자 화이트리스트**: 주요 카드사(신한·삼성·현대·국민·롯데·BC·우리·하나…) + 은행 입금 알림.
- **템플릿(정규식) per 발신자** → 추출 `{금액, 가맹점/적요, 일시, 유형(승인/입금/취소/거절)}`.
- **정규화** → `transaction(source=sms_capture, status=needs_review)` → 거래 확인 큐(S7).
- **중복/취소**: idempotency 해시 + 취소문자 매칭으로 상계.

### 5.4 백엔드 인입
- `POST /ingest` (Idempotency-Key=발신자+시각+금액+해시) → dedupe → 거래 생성.
- **페어링**: 오너가 웹에서 발급한 코드로 컴패니언 등록(`capture_device`).

### 5.5 성공 기준 (Go/No-Go)
- 파싱 정확도 **≥90%**(금액·일시 정확, 가맹점 추출) — 라벨 표본 50~100건.
- 취소/중복 **오상계 0**.
- 백그라운드 수신 **안정성**(재부팅·도즈모드 후 복구).
- **배포 경로 확인**: Play **내부 테스트**로 파일럿 가능한지 + 정책 리스크 평가.

### 5.6 작업 (1~2주 타임박스)
1. 표본 수집·라벨링(여러 카드사/은행 문자·알림).
2. Kotlin 앱: NotificationListener(+SMS) · 화이트리스트 · 로컬 파싱.
3. 파서 템플릿 + 정확도 측정 하니스.
4. 백엔드 `/ingest` 목업 + dedupe + 큐 연결.
5. **정책 리서치**: Play SMS/알림 정책, 내부테스트 배포 절차.
6. 프라이버시 설계: 동의 고지문·최소 저장.

### 5.7 리스크 & 대안 (백업 채널)
- **Play 정책 거절** → 파일럿은 **사이드로드/내부배포**, 정식은 NotificationListener 정당화 or 대안 채널.
- **iOS 불가** → 아래 보조 채널로 커버:
  - **이메일 인입(크로스플랫폼!)**: 카드사·은행 **이메일 알림**을 Gmail API/IMAP로 파싱 → iOS·PC 포함 커버. **Play 정책 무관** → 강력한 보완.
  - **영수증 OCR / 공유시트**: 수동 보완.
  - **CSV 업로드 + 수기**: 항상 가능한 기본선.
- → PoC는 **SMS(안드로이드) + 이메일(크로스플랫폼)** 를 함께 타당성 검토 권장.

### 5.8 결정 게이트
PoC 결과로 **FIN-4**를 결정: **GO**(SMS 중심) / **조정**(이메일 우선) / **보류**(CSV+수기로 MVP, 캡처는 v1).

## 6. 데이터 모델 델타 (06에 추가 제안)

- `capture_device`: studio_id, platform(`android`), paired_at, push_token, status — 오너 폰 페어링.
- `ingest_event`: studio_id, channel(`sms`/`email`), sender, received_at, raw_ref(최소), parsed(jsonb), dedupe_key, status(`parsed`/`failed`/`linked`), transaction_id? — 인입 원천·idempotency.
- `transaction.source` 이미 `sms_capture` 포함(06) → `email_capture` 추가.

> 승인 시 06에 반영.

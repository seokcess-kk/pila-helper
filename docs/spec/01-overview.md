## 1. 한 줄 정의 / 콘셉트

> **"필라테스 샵을 위한 예약·회원권·출석·상담CRM·매출·비용·수익분석 통합 경영관리 솔루션"**

필라테스 샵의 **운영(예약·출석·수강권)** 과 **경영(매출·비용·현금흐름·수익성)** 을 한 시스템에서 잇는다.
다른 예약 솔루션이 "수업을 돌리는 도구"라면, 본 솔루션은 거기에 더해 **"이번 달 우리 샵이 실제로 얼마를 벌고 있는가"를 회계 지식 없이도 답해 주는 경영 도구**다.

콘셉트를 한 문장으로 압축하면:

- **운영은 빠르게**(원장 10초·관리자 3클릭·회원 30초, §6),
- **돈은 정확하게**(결제기준 + 수업소진기준 **이중 손익**, 통장/카드 기반 **현금흐름·자동분류**, §3),
- **확장은 처음부터**(내부 샵 → SaaS 멀티테넌트, §5).

## 2. 문제 정의 — 신규 필라테스 샵의 운영 페인포인트

신규 오픈 필라테스 샵은 "회원 수는 적은데 챙길 숫자는 많은" 시기를 겪는다. 예약 솔루션은 수업을 돌려 주지만 **돈의 흐름은 사장(원장)의 머릿속과 엑셀에 흩어져 있다.** 본 솔루션은 아래 페인포인트를 정조준한다.

### 2.1 페인포인트 → 문제정의 → 본 솔루션의 응답

| # | 현장 페인포인트(원장의 말) | 문제정의 | 본 솔루션의 응답(소유 문서) |
|---|---|---|---|
| P1 | "이번 달 매출은 카드사 입금이 다 안 들어와서 통장만 보면 모르겠다." | **결제 ≠ 입금 ≠ 인식**이 뒤섞여 진짜 매출을 못 본다. | 카드매출 **승인/매입/입금 3단계**(`reconciliation_stage`) 추적 + 미입금 카드매출 지표(§3.2) |
| P2 | "회원이 끊은 10회권 중 실제로 쓴 건 3회인데, 그걸 다 번 걸로 봐도 되나?" | 선결제 매출을 **언제 번 걸로 볼지** 기준이 없다. | **이중 손익**: 결제기준 vs 수업소진기준 분리 인식(§3.1, [`19-metrics.md`](./19-metrics.md)) |
| P2 | "무통장입금 들어온 게 어느 회원 건지 매번 손으로 맞춘다." | 입금자명 ↔ 회원명 **수동 대사**에 시간이 샌다. | 금액/날짜/이름 자동추천 매칭(`bank_transactions`), 미매칭 목록(§3.3, [`17-reconciliation-policy.md`](./17-reconciliation-policy.md)) |
| P3 | "카드값·임대료·강사료가 통장에서 빠지는데 뭐가 고정비고 뭐가 광고비인지 정리가 안 된다." | 비용이 **카테고리·고정/변동**으로 안 잡혀 영업이익을 못 낸다. | 비용 17종 카테고리 + `cost_type`(고정/변동) + 거래처명 자동분류(§3.3, [`18-expense-category-policy.md`](./18-expense-category-policy.md)) |
| P4 | "누가 노쇼인지, 만료 임박이 누구인지 매일 수업 전에 찾아본다." | 노쇼·만료·미수금 **회원을 한눈에 못 본다.** | 오늘의 운영 대시보드 + 회원 태그(`no_show_risk`·`expiring`·`receivable`)([`09-admin-dashboard.md`](./09-admin-dashboard.md)) |
| P5 | "상담 온 사람이 체험까지 왔는데 등록은 몇 명이나 했는지 모른다." | 문의→체험→등록 **전환 깔때기**가 안 보인다. | 상담 CRM(`leads`·`lead_status`) + 체험 등록전환율·유입경로별 전환율([`19-metrics.md`](./19-metrics.md)) |
| P6 | "강사료를 출석 기준으로 줘야 하는데 누가 몇 타임 했는지 매달 센다." | 강사별 수업 수·기여도·정산이 **수기**다. | 출석기준 수업 수 집계 + `settlements` 정산, 강사별 수익성([`10-profit-dashboard.md`](./10-profit-dashboard.md)) |
| P7 | "회원은 전화로 예약하고, 취소도 전화로 한다. 인포가 종일 전화기다." | 회원 셀프 예약 채널이 없어 **프론트가 병목**이다. | 회원 **모바일 웹** 셀프 예약·취소·대기(§4, [`08-wireframes.md`](./08-wireframes.md)) |
| P8 | "강사한테 회원 메모는 보여주되 매출·통장은 절대 안 보였으면." | 개인/결제/수익 정보 **권한 분리**가 필요하다. | 7역할 RBAC, 강사는 전체 매출·통장 잔액 **접근 불가**(§5, [`13-rbac.md`](./13-rbac.md)) |

### 2.2 한 줄 문제정의

> 신규 필라테스 샵 원장은 **예약은 돌리지만 "지금 얼마 버는지"는 모른다.** 결제·입금·소진·환불·비용이 서로 다른 시점·장부에 흩어져 있고, 이를 통합해 **현금흐름과 진짜 영업이익을 회계 지식 없이 보여 주는 도구**가 없다.

## 3. 차별화 — 우리는 무엇이 다른가

본 솔루션의 핵심 차별화는 **(A) 이중 손익 회계 모델**과 **(B) 통장/카드 기반 현금흐름·자동분류** 두 가지다. 예약·출석·수강권은 "있어야 하는 기본기"이고, 경쟁 우위는 **돈을 다루는 방식**에 있다.

### 3.1 차별화 A — 결제기준 + 수업소진기준 **이중 손익**

같은 한 건의 결제를 **두 가지 회계 기준으로 동시에 인식**하고, 대시보드에서 토글한다. 모든 인식은 `revenue_records`에 `revenue_basis`(`payment`/`consumption`)로 분리 적재된다(CANON §4, §3.12).

#### 원장이 이해할 표현 + 정확한 산식

- **결제 기준(`revenue_basis = payment`)** — "**돈이 들어온 날** 번 것으로 친다." 현금흐름·자금관리에 유리.
- **수업 소진 기준(`revenue_basis = consumption`)** — "**수업을 쓴 만큼** 번 것으로 친다." 원가·강사료·수익성 분석에 유리.

**예시 — 60만 원 / 10회권을 6월 1일에 결제, 6월에 3회 출석:**

| 단가 산식 | `passes.unit_price_amount` = `round(purchases.final_amount / passes.total_count)` = `round(600,000 / 10)` = **60,000원/회** |
|---|---|

| 6월 인식 매출 | 산식 | 금액 |
|---|---|---|
| **결제기준** | 결제 전액을 6/1에 인식 (`amount = paid_amount`) | **600,000원** |
| **수업소진기준** | 60,000원 × 3회(출석/차감분만) | **180,000원** |

> 두 숫자는 **둘 다 맞다.** 결제기준은 "통장에 들어온 돈", 소진기준은 "이번 달 실제로 제공한 서비스의 값"이다. 본 솔루션은 둘을 **합산하지 않고 기준별로만** 보여 주어(중복 합산 금지, CANON §4) 원장이 자금과 수익성을 각각 정확히 본다.

- **환불 반영(결제기준)**: `refunds` 발생 시 `revenue_basis='payment'`, `source_type='refund'`, `amount = -refund_amount`(음수) 1건 추가 → 순매출 자동 차감.
- **순매출 산식(공유)**: 순매출 = Σ`revenue_records.amount`(선택 basis, 환불 음수 포함) — 상세는 [`19-metrics.md`](./19-metrics.md), 모델은 CANON §4.4.

### 3.2 차별화 B-1 — 카드매출 3단계 추적(현금흐름)

현장 카드결제는 **승인 ≠ 매입 ≠ 입금**이다. `card_sales`가 3단계(`reconciliation_stage`: `approved`/`captured`/`deposited`)를 추적해 "**아직 통장에 안 들어온 카드매출**"을 보여 준다(CANON §3.21).

- **미입금 카드매출 산식**: Σ`card_sales.net_deposit_amount` where `reconciliation_stage != deposited`
- **실입금 산식**: `net_deposit_amount` = `amount − fee_amount` (카드수수료 추정율 기본 `card_fee_rate = 0.023`, CANON §6.3)

| 단계(코드) | 라벨 | 원장이 보는 의미 |
|---|---|---|
| `approved` | 승인 | "결제는 됐지만 통장엔 아직" |
| `captured` | 매입 | "카드사가 매입 처리함" |
| `deposited` | 입금 | "통장에 실제 입금 + 통장거래 매칭 완료" |

### 3.3 차별화 B-2 — 통장/카드 자동분류(비용·매칭)

사업자 통장 입출금과 카드 사용내역을 끌어와 **매출/비용/이체/기타로 자동 분류**하고, 거래처명 기반 규칙(`transaction_matching_rules`)으로 **한 번 고친 분류를 다음 거래부터 자동 적용**한다(정본 §7·§18 원칙).

- 입금: 입금자명 ↔ 회원명 **자동추천 매칭** → `payments`와 연결(미수금/입금대기 해소).
- 출금/카드사용: 거래처명 규칙으로 `expense_category`(17종) + `cost_type`(고정/변동) 자동 분류.
- 미매칭 거래는 별도 목록으로 노출, 관리자가 손쉽게 `match_target`(`revenue`/`expense`/`transfer`/`etc`) 지정.

### 3.4 벤치마크 대비 포지셔닝

> 벤치마크(스튜디오메이트·바디코디·아하루)는 **참고만** 하며 문구·구조를 복제하지 않는다. 아래 표는 일반적으로 알려진 카테고리 수준의 포지셔닝 비교이며, 우리의 핵심 차별점은 **수익분석·경영관리·현금흐름**이다.

| 영역 | 스튜디오메이트(참고) | 바디코디(참고) | 아하루(참고) | **본 솔루션** |
|---|---|---|---|---|
| 예약·출석·수강권 | 강점 | 강점 | 강점 | 기본 충족(차별점 아님) |
| 회원 모바일 셀프예약 | 지원 | 지원 | 지원 | 지원(모바일 웹) |
| 상담 CRM(문의→체험→등록 전환) | 부분 | 부분 | 부분 | **전환 깔때기 + 유입경로별 전환·수익성** |
| **결제기준 + 소진기준 이중 손익** | 약함 | 약함 | 약함 | **핵심 차별화(이중 인식·토글)** |
| **통장/카드 기반 현금흐름·자동분류** | 약함 | 약함 | 약함 | **핵심 차별화(3단계 입금·거래 매칭)** |
| 영업이익·월말 예상 손익 | 약함 | 약함 | 약함 | **원장 대시보드 핵심 지표** |
| 비용 관리(17종·고정/변동) | 약함 | 약함 | 약함 | **카테고리 자동분류 + 손익 연결** |
| SaaS 멀티테넌트(다지점·과금) | 지원 | 부분 | 부분 | **MVP부터 구조 내장(`tenant_id`+`studio_id`)** |

**포지셔닝 한 줄**: *"예약 솔루션이 아니라, 예약까지 되는 **필라테스 경영관리 솔루션**."*

|---|---|---|
| 수업 유형 | **1:1 개인레슨 + 그룹레슨** 중심(+ 체험) | `class_type`: `personal`/`group`/`trial`(§3.3) |
| 회원권 | **횟수권 중심**(1:1권·그룹권·체험권·패키지권) | `pass_kind`: `personal`/`group`/`trial`/`package`(§3.7) |
| 결제 수단 | **현장 카드결제 + 무통장입금/계좌이체 + 현금** | `payment_method`: `card_onsite`/`transfer`/`cash`(§3.11) |
| 결제 상태 | 결제완료/입금대기/일부입금/미수금/환불완료 | `payment_status`(§3.10) — **미수금 관리 포함** |

| 통장/카드 | **MVP: CSV 업로드 + 수동 등록/매칭** | `bank_transactions`·`card_expenses`·`card_sales` |
| 데이터 격리 | **MVP부터 SaaS 확장 가능** 구조 | `tenant_id` + `studio_id`(CANON §1.2) |

> 결제기준 vs 수업소진기준은 **항상 구분**한다(정본 §UX 원칙). 예: 현장 카드결제는 결제기준에서 즉시 인식되지만(입금 전이면 미입금 카드매출로 별도 표시), 소진기준에서는 회원이 수업을 쓸 때마다 인식된다.

## 5. 단계 비전 — 내부 샵 → SaaS 멀티테넌트

데이터 구조는 **처음부터 멀티테넌트**(`tenant_id` + `studio_id`)로 설계하되, 기능은 단계적으로 켠다. MVP에서도 "한 샵을 위한 단순한 화면"으로 보이지만, **그 아래 스키마는 이미 SaaS·금융연동을 견딘다**(정본 §주의사항).

| 단계 | 무대 | 켜지는 핵심 기능 | 대표 테이블/구조 |
|---|---|---|---|
| **1차(MVP) — 내부 샵 운영** | 우리 샵 1개 | 회원·상담·수업·예약·출석·횟수권·수동결제/미수금·비용 수동입력·통장/카드 **CSV 업로드**·기본 매출/비용/손익 대시보드·역할별 권한·수정/삭제 로그 | `members`·`reservations`·`passes`·`payments`·`expense_records`·`revenue_records`·`audit_logs` |
| **2차 — 자동화·심화 경영분석** | 우리 샵(고도화) | 거래 **자동분류**·입금 **자동매칭**·카드매출 입금 대조·반복비용·**월말 예상 손익**·강사별/수업별/유입경로별 수익성·재등록 자동화·알림톡·운동일지/강사 코멘트 | `transaction_matching_rules`·`card_sales`·`settlements`·`notifications` |
| **3차 — SaaS·금융연동 개방** | 다수 샵(외부 온보딩) | 오픈뱅킹·카드매출 통합조회·PG 온라인결제·전자계약·네이버 예약/플레이스·**다지점**·**SaaS 요금제/사용량 과금**·세무 리포트 내보내기 | `external_integrations`·`subscription_plans`·`tenant_subscriptions`·`financial_reports` |

상세 범위는 [`05-scope-mvp.md`](./05-scope-mvp.md) · [`06-scope-phases.md`](./06-scope-phases.md) · 일정은 [`21-roadmap.md`](./21-roadmap.md), 아키텍처는 [`20-saas-architecture.md`](./20-saas-architecture.md)가 소유한다.

## 6. 핵심 성공지표(KPI) + UX 원칙

### 6.1 UX 원칙 — 속도 3대 약속(정본 §18)

| 대상 | 약속 | 측정 정의 | 설계 함의 |
|---|---|---|---|
| **원장(owner)** | 오늘 운영 + 이번 달 수익을 **10초** 안에 파악 | 로그인 후 대시보드 첫 화면 도달 ~ 4영역(오늘운영/매출/비용/수익) 인지까지 ≤ 10초 | 단일 화면 요약·핵심 숫자 우선([`09-admin-dashboard.md`](./09-admin-dashboard.md)) |
| **관리자(manager)** | 회원 등록·예약 변경·수강권 부여·결제 입력을 **3번 클릭** 안에 | 진입 ~ 저장까지 클릭/탭 ≤ 3 | 빠른 액션·최소 입력·기본값 선채움([`08-wireframes.md`](./08-wireframes.md)) |
| **회원(member)** | 모바일 웹에서 예약을 **30초** 안에 완료 | 예약 페이지 진입 ~ 예약 완료 알림까지 ≤ 30초 | 모바일 우선·단계 최소화·즉시 확정 |

추가 UX 원칙(정본 §18): 수익분석은 **회계 지식 없이도 이해 가능**, 통장/카드는 **자동분류하되 쉽게 수정**, **한 번 고친 분류는 다음부터 자동 적용**, **결제기준 vs 소진기준 구분 표시**, 개인/결제/수익 정보 **권한별 엄격 제한**, **모든 금전 수정은 로그**.

### 6.2 제품 성공지표(우리가 잘 풀었는지)

| KPI | 정의 | 목표 신호 |
|---|---|---|
| 원장 대시보드 도달 시간 | 로그인 → 수익 인지(중앙값) | ≤ 10초 |
| 관리자 핵심 액션 클릭 수 | 회원/예약/수강권/결제 입력 평균 클릭 | ≤ 3클릭 |
| 회원 셀프 예약 완료 시간 | 모바일 웹 예약(중앙값) | ≤ 30초 |
| 거래 자동분류 적중률 | 자동분류가 관리자 수정 없이 유지된 비율 | 2차에서 ≥ 80% |
| 입금 자동매칭률 | 입금거래 ↔ 결제 자동 매칭 비율 | 2차에서 ≥ 70% |

### 6.3 샵 경영지표(고객이 본 솔루션으로 보게 되는 숫자 — [`19-metrics.md`](./19-metrics.md) 소유)

원장이 대시보드에서 추적하는 대표 경영지표(정본 §8):

- **수익성**: 영업이익 = 순매출 − 총비용 / 영업이익률 = 영업이익 ÷ 순매출
- **현금흐름**: 현재 통장 잔액 · 미입금 카드매출 · 미수금 · 예상 지출 · 월말 예상 현금잔고
- **단위경제**: 회원 1인당 평균 매출 · 1인당 평균 이익 · 신규회원 **CAC** · 회원 **LTV**
- **전환·유지**: 체험 등록전환율 · **재등록률** · 유입경로별 전환·수익성
- **수업 수익성**: 1:1 수익성 · 그룹 수익성 · 강사별 수익성(소진기준 기반, §3.1)

> 모든 산식의 정의·소유는 [`19-metrics.md`](./19-metrics.md), 회계 모델 원천은 CANON §4에 있다. 본 문서는 개요로서 대표 지표만 제시한다.

## 7. 한눈 요약

- **무엇**: 필라테스 샵 예약·회원권·출석·상담CRM·매출·비용·**수익분석** 통합 경영관리 SaaS.
- **누구의 문제**: 신규 샵 원장이 "지금 얼마 버는지" 모르는 문제(결제·입금·소진·환불·비용이 흩어짐).
- **어떻게 다른가**: ① 결제기준 + 수업소진기준 **이중 손익**, ② 통장/카드 기반 **현금흐름·자동분류**.
- **타깃·조건**: 1:1/그룹·횟수권·현장카드+무통장입금·회원 모바일 웹.
- **비전**: 내부 샵 → 2차 자동화 → 3차 SaaS·금융연동.
- **약속**: 원장 10초 · 관리자 3클릭 · 회원 30초.
